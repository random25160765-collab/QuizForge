# 日程调度：谁决定放在哪

> **计划说「要做什么」，日历说「什么时候做」，这一层说「凭什么放在那一刻」。**
>
> 2026-11-08。自动排程不是"把待办倒进日历"，是把**身体状态**与**既有事实**
> 摊成一份约束，交给求解器，然后给出每一块的**理由**与排不进去的**原因**。
> 人只负责确认与撤销 —— 因为唯一不可外包的是判断。

## 一、三方事实，各有各的边界

一张日历上同时躺着三种东西，它们"谁说了算"完全不同。这个区分是整层的地基，
先把它钉死，其余都是推论：

| 来源 | 判据 | 同步 | 重排 |
| --- | --- | --- | --- |
| **订阅（课表）** | `sub_id` 非空 | 会被订阅内容更新 | **永不移动** |
| **用户手动 / 钉住** | `run_id` 为空，或 `locked`，或 `detached` | 不动 | **永不移动** |
| **求解器产出** | `run_id` 非空且未锁、未改 | 不动 | **只回收这一批** |

* `detached` = 用户拖过 / 改过这一块。**订阅是别处的事实，但"我把这节课挪到晚上"
  也是事实** —— 一旦动过就冻结，同步与重排都不许盖回去。
* `locked` = 用户钉住。与 `detached` 是两套理由：前者是"别动我"，后者是"这已经是我的了"。
* `run_id` = 哪一次重排排的。重排只回收自己人排的块 —— 手工建的不碰、钉住的不碰、
  别人那一轮的也不碰。撤销同理：只回滚**这一次**动过的行。

## 二、健康是框架，不是公式

`app/wellbeing/` 里没有"睡眠公式"，只有四个注册表：

| 扩展点 | 职责 | 内置 |
| --- | --- | --- |
| `Metric` | 从原始记录算一个 0–1 的值（带原文与解释） | `sleep_debt` / `last_night` / `study_load` / `circadian` |
| `Profile` | 把若干 Metric 组合成 **48 槽精力曲线** + `deepBudgetMin` + 一句人话 | `standard` / `recovery`（`cram` 预留） |
| `Advisory` | 结构化的"今天该怎么对自己"：`schedule_constraint` / `chat_intervention` / `ui_note` | 睡前宵禁、深度预算、恢复期、睡眠债 |
| `Regime` | 某天用哪套档位（`health_regimes` 表，带起止日期） | — |

关键约定：

* **对话侧只读 `chat_intervention`**。劝睡不是 `chat.py` 里写死的 `if hour > 23`，
  而是一条建议；`severity == "hard"` 才允许要求模型"压过话题、只回一句"。
  以后加"病了就别学了"，改的是建议，不是对话代码。
* **求解器不知道"睡眠债"这三个字**。健康侧把状态翻译成约束（IR），求解器只认 IR。
  这条是"可插拔"的硬指标：测试里注册一条新建议，断言 IR 里出现它、排程随之改变。
* 每次重排把当时的 `profile` 与 `regime_id` 记进 `schedule_runs` ——
  事后能回答"那天为什么只排了两小时"。

## 三、约束 IR：健康与求解器之间唯一的接口

`app/schedule_ir.py` 定义 `Constraint(kind, scope, params, source, weight)`。
`kind` 是闭集，拼错立刻报错（否则会静默失效，最难查）。

**硬约束**（不满足就不排）：

| kind | 含义 |
| --- | --- |
| `no_window` | 这段不排（睡眠、三餐） |
| `max_minutes` | 当天总时长上限 |
| `max_deep_minutes` | 当天**深度用脑**上限（恢复期可能只有 1 小时） |
| `deadline` | 截止日之后不排 |
| `energy_floor` | 深度任务要先过这条精力线 |
| `cooldown_after` | 下课 20–30 分钟内不进深度任务 |

**软约束**（只影响"怎么排"，不影响"排不排"）：

`prefer_window`（上午优先）、`alternate_domain`（文理交替）、
`cap_topic_minutes`（单日单主题上限）、`prefer_early_for_deadline`、
`minimize_fragment`（分块并天）、`priority_boost`（门禁没过的往前站）。

其中 `cap_topic_minutes` 在 CP-SAT 里是**超额罚分**（不是禁止，且 `other` 不算主题）；
`alternate_domain` 与 `minimize_fragment` 要对"相邻 / 同任务的两块"建模，
成对变量会让规模炸，所以放在**求解之后**做一次确定性的局部改进 —— 两个引擎共享，
挪不动就保持原样。

新增一种健康策略 = 多吐一条 IR，**不改求解器**。

## 四、求解

`ScheduleInput(tasks, fixed, energy[48], constraints, options, horizon, previous)` →
`Solution(blocks[], unscheduled[], engine, stats, constraints)`。

* 30 分钟对齐；`SLOT = 30`，一天 48 槽。
* 两套实现共用同一份 IR：**CP-SAT**（`ortools`，可选依赖）与**纯 Python 后备**
  （贪心 + 局部改进）。`ortools` 不在就自动降级，输出里带 `engine` 字段。
* 确定性：固定变量顺序、单 worker、`random_seed=0`。同一份输入两次求解逐块相同 ——
  差异高亮与撤销都靠这个前提。
* **保守**：上一轮的位置在目标函数里有 +40 的软偏好。加一条待办不该让整周洗牌；
  测试钉住"加一条，`moved` 必须是 0"。
* **排不进去要说原因**：`explain_unscheduled` 按可查证的判据给一句话
  （截止日已过 / 开始日超范围 / 整块超 240 分钟 / 没够精力的空档 / 位置被占满）。
* **长任务排多少算多少**：一条待办被切成若干块铺到多天；七天排不完时，**能排几块
  排几块**，剩下的以"这周排下 12h，还差 8h"进 `unscheduled`，下次重排接着排。
  一轮最多看 `天数 × 3` 块（`MAX_CHUNKS_PER_DAY`）—— 那是求解规模的上限，
  不是"一天只能学三块"的规矩；超出的部分同样折成剩余分钟报出来。

一个块长这样：`30–240 分钟`、按 `max_chunk_min`（默认 90）均分；
`focus ∈ {light, medium, deep}` 决定它要不要过精力门槛；
`domain ∈ {art, science, skill, other}` 文本交替用（`other` 不算主题）。

## 五、重排与撤销

`POST /api/schedule/replan {horizonDays?, apply?}`：

1. 读窗口内的块与未完成待办，组装 IR（含门禁的 `priority_boost`），求解；
2. 算差异（按 `item_id` 认身份：时间集合没变就是"没动"，连 id 都不换）；
3. `apply=false` 只返回提案卡；`apply=true` 才落库，并写一条 `schedule_runs`。

`POST /api/schedule/runs/{id}/undo`：删掉这次新建的行、按 `before` 快照把被删 / 被挪的行
原样写回（连 `created_at` 一起）。**不是全库回滚** —— 重排之后用户手动改的别的东西，
一动不动。一条 run 只能撤一次，再撤是 409。

## 六、门禁是协议，不是判分器

`app/gates.py` 的每个策略实现同一对方法：

```python
prepare(db, item, event)        -> 给用户看的那张卷子（不带答案）
verify(db, item, event, answer) -> GateResult(passed, score, detail, payload)
```

内置五种：`quiz`（题库抽题，2/3 通过）、`recall`、`explain`、`artifact`、`none`。
界面只认 `kind`（`quiz` 画选项、`text` 画多行输入、`none` 直接放行）——
所以加一种门禁不需要改路由与前端。

* **没通过也落库**（`gate_runs`）。它是"下一次重排该优先补偿谁"的唯一依据；
  只记通过的话，没过的块静默留在原地，第二天照旧排在最后。
* 没通过**不把条目勾上**（`done` 保持 False）。
* 没有 AI 判分时降级为自评，`payload.degraded = true` —— 宁可标出来，也不假装判过。

## 七、扩展方式（照抄即可）

**加一个指标**：`wellbeing/metrics.py` 写个 `Metric` 子类 → `register_metric(...)`。

**加一套档位**：写个 `Profile` 子类（实现 `curve`）→ `register_profile(...)`；
设置页的下拉从 `/api/wellbeing/profiles` 读，自动出现。

**加一条建议**：写个 `Advisory`，返回 `Advice(kind=...)`；
`kind=schedule_constraint` 时 `params={"rule": ..., ...}` 就是一条 IR。

**加一种门禁**：`register(Gate子类)`；界面按 `kind` 自动画。

**改排程策略**：改 IR 或改目标函数权重，不要往 `scheduler.py` 里塞业务判断。

## 八、有意没做

* **不学用户的偏好**：权重是显式的、可解释的。学出来的顺序说不出理由，
  而这一层最需要的恰恰是"为什么排在这"。
* **一块不跨午夜**：块是"一次坐下来"，跨了午夜那半段就没有精力曲线可言。
  但这**只管块、不管任务** —— 一条要几十小时的活儿会切成几十块铺到整周，
  这周铺不完的带着"还差多少"排到下周（见 §四）。
* **不自动改计划**：排程只动日历，不动"要做什么"。
* **不做多人/共享日历**：订阅是只读的外部事实，不是协作面。
