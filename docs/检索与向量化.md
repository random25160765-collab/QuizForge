# 检索与向量化

写于 **2026-09-21**。起因是加「练习中心 · 抽认卡」之前的一次反问：

> 这个决策根本就是错的！技术领域的近义词可多着呢，你也不能要求我每次都原原本本说出原词来啊。

这份文档做三件事：把**现状**记成可核对的事实、说清**错在哪**、写下**要去的方向**
（资料库 = 原始资料 + 由资料打成的向量库）。每条事实都带 `文件:行号`。

---

## 一、现状

### 1.1 检索 = 两路召回 + 代理式回读

`api/app/materials.py:1-28` 的模块注释把方案称作 **"三路召回（规则 → 图 → 向量）"**，
并交代只做了第一路：

| | 谁 | 实现 | 本质 |
|---|---|---|---|
| ① 规则 / 字面 | `materials.search`（`materials.py:116`） | 查询按空格切词，**所有词必须同时出现在同一行**才算命中 | 行级子串匹配 |
| ② 图 | `search_knowledge`（`tools.py`） | `ILIKE '%q%'` 打 concept 的 key/name/definition/aliases + knowledge_point 的 key/name，再沿 `point_sources` 回到行区间 | **也是子串匹配**，只是换到了结构化表上 + 结构化邻域 |
| ③ 代理式回读 | `read_material` / `attach_material` | 按 `(slug, 行区间)` 精读（默认 60 行 / 6k 字） | 让前两路够用的那一环 |

③ 有一条硬性质值得单独记住：`read_material` 与前端"点开引用"调的是**同一个函数**
（`materials.read_lines`，`materials.py:79`），所以模型看到的那几行与用户看到的**逐字一致**。
"引用能当证据"靠的就是这一条。

字面检索的限额（`materials.py:40-50`）：一次最多扫 **40 份材料**、读 **200 行**、单行截 300 字；
返回里带 `scanned` / `total`；进程内 `lru_cache` 缓存 12 份正文。全库 71M 文本首次约 2 秒。

### 1.2 资料在后端是**三套并存的文本存储**

| | **A 资料库**（library） | **B 材料 / 知识空间**（materials） | **C 笔记** |
|---|---|---|---|
| 权威 | 文件系统 | SQLite | 文件系统 |
| 元数据 | `data/library/{citekey}.yaml` | `materials` 表 | 文件 YAML 头 |
| 正文 | **抽出来缓存**：`data/library/.text/{citekey}.txt` + `.meta.json`（质量判定） | **不抽**，只存 `source_path` **绝对路径**，正文永远在原文件里 | `.md` / `.canvas` / `.outline` 本身 |
| 源文件 | 用户的资料根（只读） | 仓库外的原文件 | `data/notes/` |
| 入库 | HTTP：`POST /api/library/index`（上传 → 抽取 → LLM 判元数据 → 冻结 yaml） | **CLI**：`python -m pipeline.ingest` / `dbsync`（**没有 HTTP 入库口**） | 界面上直接写 |
| 检索 | `lib.search`（表达式 + 子串，整篇进池） | `materials.search`（行内 AND） | notelib（表达式 + 子串） |
| **行坐标** | **没有**（只有"条目 + 正文节选"） | **有**：`material_slices` + `point_sources` | 没有 |

真实磁盘（`ls` 实测）：`data/quizforge.db` · `data/library/{59 yaml, .text/112, .orphans/7}` ·
`data/notes/Math/…` · `data/cache/pyodide/`。

agent 手上的工具**跨着两套**（所以会觉得"怎么有两份资料库"）：

| 工具 | 打在哪 |
|---|---|
| `attach_material` | A 资料库（按 citekey） |
| `search_material` / `read_material` | B 材料（按 slug + 行区间） |
| `search_knowledge` / `get_point_detail` / `explore_graph` | B 的图谱部分 |
| `search_notes` / `write_note` | C 笔记 |

### 1.3 出题机已经在材料上打了一整套标记 —— **这是向量化现成的骨架**

流水线（`pipeline/`）不是"出题"一件事，它先**读懂材料**：

| 步骤 | 产物 | 落在哪 | 内容 |
|---|---|---|---|
| `ingest` | **切片** | `material_slices` | `slice_id`=`sl-NNN`、`path`=`文件名#L起-L止`、`start_line/end_line`、`tokens`（字数÷3.6 粗估）、`figures`、`summary`（该片标题） |
| `ingest` | 图 | `material_figures` | `figure_id`、`src`、`slice_id`、行区间、`caption`、`kind`、`keys` |
| `worker --kind=extract` | **候选知识点** | `point_candidates` | 每个切片用模型抽出：`key/name/kind/thickness/layers/sources/terms/raw`；读图事实也进这张表（`origin=figure`） |
| `resolve` | 归并结果 | `maps/<材料>/coverage.yaml`（历史形态） | 模型只做判断（合并/拆分/丢弃），**字段由代码组装**（`resolve.py:5`） |
| `dbsync` | **正式知识点** | `knowledge_points` | + `producible = bool(sources) and thickness>0` |
| `dbsync` | **出处** | `point_sources` | `point_id, slice_id, start_line, end_line` —— 注释写着"**整个流水线的地基**，校验员只认它"（`models.py:573-589`） |
| `dbsync` | 点之间的弱边 | `point_edges` | `same_section` / `shares_terms` / `part_of` |
| `graph_build` | **概念** | `concepts` | 纯规则归并（同 key → 同名 → 术语重合，阈值 3 / 0.5）；每个点是"概念在某材料的一次出现" |
| `graph_build` / `graph_log` | 概念边 | `concept_edges` | 五类：`requires` / `part_of` / `contrast_with` / `implements` / `co_occurs`，带 `derived_by=code\|llm\|human` |
| `worker --kind=author` | 题 | `questions`（draft→verified→published） | — |
| `dbstore.save_verdict` | 题↔点 | `question_points` | **只在校验通过时写** |
| `graph_build.link_questions` | 题↔概念 | `question_concepts` | 覆盖率/选题以它为准 |

**切片是最值得注意的一件**（`ingest.split_slices`，`ingest.py:49-81`）：

* 按 Markdown **`##` / `###` 标题**切 —— 也就是**跟着作者的章节结构走**，不是定长 chunk；
* 长度约束：`MIN_LINES=40`（更短并进下一片）、`MAX_LINES=400`、`SPLIT_AT=250`；
* 行区间 1-based 闭区间，**相邻片无重叠**（设计文档建议留 1–2 段重叠，实现没做）；
* 实测规模：60 份材料 → **215 片**（1–17 片/份，多数 1–3 片）。

**出处那条链**（"点开引用回到原文"靠它）：`point_sources` 是唯一权威；
模型写"逐字引用"、程序把它定位成行号（`worker.locate_quote`，`worker.py:184-219`，
注释："引用是模型擅长的，行号是程序擅长的"）；回读是 `materials.read_lines`。

### 1.4 向量：只有接口占位，零产物，而且当前 provider 给不了

* `pipeline/llm.py:252` 有一个**完整可用的** `embed()`（OpenAI 兼容 `/embeddings`，带 6 次重试）；
* `pipeline/config.py:83` 有 `embed_model`，默认 `"text-embedding-3-small"`；
* **全仓库没有任何调用点**（`\.embed\(` 只命中定义处）；`store.py` 注释提到"见 embeddings 表"，
  但那张表不存在（`store.py:21-41` 只有 `tasks`）；
* 更硬的阻塞：当前内测通道的端点是 `api.deepseek.com/v1`，实测 `/v1/models` 只给
  `deepseek-flash` / `deepseek-v4-pro` —— **没有 embedding 模型**。那个默认值指向一个
  这个 provider 根本不提供的模型。

所以：向量化在这套东西里**一行都还没跑过**。

## 二、错在哪

### 2.1 `THESIS` 那句论证本身是对的，但它被**套用**到了两个不同的问题上

`docs/THESIS.md:85-88`：

> **关系不靠标注，也不靠向量。**……向量数据库在这里是用错了地方：向量距离是**对称的**、
> 只表示"像不像"，而前置关系是**反对称的**（A 是 B 的前提，反之不成立）。

这段话对**关系**是对的：前置关系要反对称、要能说清"为什么是前提"，向量给不了。
但到了 `THESIS.md:102` 与 `:121` 变成了**全局结论**：

> 4. **工具**：错题本 + SM2 + 间隔复习 + 掌握度 + 前置约束，是"自适应"的最小可行集合；**别上向量库。**
> | 智适应用前置约束，不用向量库 | `api/app/mastery.py` + SM2 + 覆盖矩阵的 `requires` |

两件事被混成了一件：

| 问题 | 要的性质 | 向量合适吗 |
|---|---|---|
| **关系**：A 是不是 B 的前提 | 反对称、可解释 | ✗ 不合适（thesis 说得对） |
| **检索**：这句话跟哪一段讲的是同一件事 | **对称**的"像不像" | ✓ **正合适** —— 对称性在这里不是缺点，是需求本身 |

检索本来就**不需要**反对称：问"三角掩码"和问"causal mask"该找回同一段。
把"关系不该用向量"的结论伸到"检索也不该用向量"，是一次**套用**。
`materials.py:16-21` 那条"为什么先做字面"又给它补了个理由（"用户的问法常常就是文档里的原词"），
于是这个决定看起来有两重支撑，其实两重都不成立。

### 2.2 "字面够用"是一个关于**用户行为**的赌注

`materials.py:16-21` 的原话：

> 材料是技术文档，问法常常就是文档里的原词（`exp_approx_mode`、`circular buffer`、函数名、配置项），
> 字面命中率本来就高；而且它**可解释**：命中了哪几行、几次，都能说清。

前半句的前提是"用户会照原文的词问"。这个前提把检索的活儿推给了人 —— 而用户的原话已经说了：

> 技术领域的近义词可多着呢，你也不能要求我每次都原原本本说出原词来啊。

技术领域的同义面本来就宽：

| 材料里写的 | 他会怎么说 |
|---|---|
| `attention mask` / `causal mask` | 三角掩码、上三角屏蔽、因果遮罩 |
| `latency` | 时延、延迟、响应时间 |
| `prefetch` | 预取、预读、提前取 |
| `bank conflict` | 存储体冲突、bank 冲突 |

字面检索的真实能力应该被如实描述成：**"你记得原词时它很快"**，而不是"它能找到你要的东西"。
这两句差别很大，而文档里写的是后者的口气。

### 2.3 代价现在落在谁身上

* **落在用户身上**：他得自己先想出原词 —— 正是这次被指出的那件事；
* **落在模型身上**：agent 只能靠换词试探，一轮里好几次 `search_material`（实测一轮 4 次搜索都常见）；
* **落在结构上**：同一件事的知识散在切片 / 知识点 / 概念三处，而只有字面这一条线能把它们串起来。

## 三、往哪去：资料库 = 原始资料 + 由资料打成的向量库

### 3.1 粒度：用**已有的切片**，不要另切一遍

切片已经同时具备三件我们想要的东西：

1. **语义单元** —— 跟着作者的 `##` 标题走，一段话不会被从中间劈开（定长 chunk 的典型毛病）；
2. **精确行坐标** —— `start_line/end_line` 现成，召回之后能直接给"哪几行"；
3. **附带的元信息** —— `summary`（标题）、`tokens`、`figures`，以及该片抽出的候选点/知识点。

也就是说：**出题机已经替我们把"chunking"做完了，而且做得比定长切法好。**

实测规模让这件事比预想的小得多：

```
材料 60 · 切片 215 · 知识点 981 · 概念 912 · 出处 2375 · 概念边 3992 · 题 2055（在架 1619）
```

215 × 1536 维 float32 ≈ **1.3 MB**。这个量级下，暴力算余弦是毫秒级的事 ——
**先别上专用向量库**（那会引入一个和现有 SQLite 不同步的新基础设施，
正是 `notelib.py:473` 拒绝倒排索引时说的那个理由）。放 SQLite 一列 BLOB 甚至直接进内存都够。

### 3.2 向量负责召回，图负责关系 —— 两者不是同一件事

| 谁回答什么问题 | 用什么 |
|---|---|
| "这句话/这个词，材料里哪一段在讲同一件事？" | **向量**（对称的相似度） |
| "A 和 B 是什么关系？先学哪个？易混在哪？" | **图**（反对称、可解释的边） |
| "这句话在原文的哪几行？" | **`point_sources` / 行区间**（唯一权威，不是向量） |

三者是**串联**的：向量把范围收窄到几片 → 图给出结构（这片属于哪个概念、它的前置是什么）→
行区间给出可点开的原文。现在缺的是第一环。

### 3.3 出处仍然只有一处权威

向量只回答"像不像"，**永远不回答"原文在哪一行"**。召回之后仍旧走
`point_sources` / `material_slices` 的行区间，回读仍旧是 `materials.read_lines`
（与前端引用同源）。这条不能含糊 —— 一旦让向量去"生成"出处，引用就不能当证据了。

### 3.4 入库口有两个，向量化该挂在哪

| | 入库口 | 有没有行坐标 | 向量化挂哪 |
|---|---|---|---|
| B 材料 | CLI 流水线（`ingest` → …） | **有**（切片 + 出处） | `ingest` 之后最自然 —— 切片现成 |
| A 资料库 | HTTP `POST /api/library/index` | **没有** | 要另定粒度（整篇？按段落？），切完仍无行坐标 |
| C 笔记 | 界面上直接写 | 没有 | — |

## 四、要拍板的（都还没定，别当成已定）

1. **先向量化哪一套？** 我倾向 **B（材料）**：它已经是"切片 + 行坐标"，而题库、图谱、
   引用全长在它上面。A 资料库是"整篇读"，切它得另定粒度，且切完还是没有行坐标。
2. **嵌入模型从哪来？** 现在这个 provider 给不了（§1.4 实测）。要么加一个能出向量的
   provider（OpenAI `text-embedding-3-small`、或国内 bge / 智谱 / 阿里），
   要么本地跑一个小模型。这是**唯一的外部阻塞**，其余都是内部工作。
3. **向量存哪？** 按 215 片的规模，SQLite 一列 BLOB（float32 打包）就够，不必上专用库。
4. **谁触发重建？** `ingest` 之后 / 一条 make 目标 / 只在正文 `sha256` 变了时重算（材料表已有该列）。
5. **要不要同时向量化知识点（981）与概念（912）？** 它们各有 `definition` / `note` / `aliases`，
   现在 `search_knowledge` 就是 `ILIKE` 打在这三列上 —— 那一处也同样吃同义词的亏。
6. **抽认卡挂哪一层？** 知识点（`knowledge_points`）还是概念（`concepts`）——
   与题同一层最省事（题挂 `question_points`）。

## 五、与「抽认卡」的关系（一句话版）

* 卡片挂**知识点**、掌握度复用 `records` + `theme/runtime/sm2.js` —— 这两件**已经在了**，
  真要接的是现有那套（`records` 的字段被刻意劈成"计数只由流水维护 / 主观补丁走 LWW"两半，
  卡片要接就得守这条规矩）；
* 卡片的"背面点开看原文"**只有 B 那套给得起**（`point_sources` 有行坐标）；
* 卡片的检索同样吃同义词的亏 —— 所以"向量化"和"抽认卡"这两件事其实是**同一件事的两半**：
  都要把"按意思找"补上。
