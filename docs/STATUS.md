## 一、形态（一句话）

**对话是前台，题与图是后台。** 学习者在 `chat.html` 里问、被推题、**被现编题**、就地作答；
判分与写回走的仍是刷题页那条路，掌握度 / SM2 / 收藏夹还是同一份记录。

**题有三个来处**，练习与组卷按 `scope=public|mine|all` 区分、卡片上「我的题单」带徽章：

| 来处 | 谁生成 | 落在哪 |
|---|---|---|
| 题库里挑（`push_question`） | 预先出好 | `questions`（权威表） |
| **模型现编**（`create_question`） | 当场 | **不落库**，只挂一张**临时题卡**；按「存进我的题单」才进 `my_questions` |
| 自己攒的 | 用户 / 上面那条存下来的 | `my_questions`（与公共题库**分开的一张表**） |

sha256（清单 `build/pyodide-manifest.json` 跟着包走，离线也能判断）。前端产物 `api/web/`
**5.2 MB**（默认不拷 Pyodide；要自包含用 `make web-full`）。**不用 Electron**（用户要求保持轻量）。

SQLite 逼出来的六件事（都不是"换个驱动"那么简单，逐条都留了注释）：
① `= ANY(…)` → `IN :x` + `expanding`；② 裸 SQL 读 JSON 列拿到的是**字符串**（PG 给 dict）
→ 统一走 `app.db.as_json`；③ `least/greatest/FILTER (WHERE …)/bool_or/now()` 都是 PG 专有
→ `case` / `COUNT(DISTINCT CASE …)` / `MAX` / `CURRENT_TIMESTAMP`；
④ `BigInteger` 主键在 SQLite 上**不自增**（只认 `INTEGER PRIMARY KEY`）→ `BigAutoId`；
⑤ SQLite **没有时区类型**，读回来是 naive，`timestamp()` 按本地时区算 → `UtcDateTime`；
⑥ `DISTINCT ON` 在 SQLite 上被**静默忽略**（比报错更糟）→ 窗口函数。

- **2026-09-21** —— **向量检索改走本地小模型 + 窗口化**（原先那版是远程通道 + 整片嵌入，
  两处都被实测否掉了）。四条决定，每条都有实测撑着：
  ① **本地而不是远程**：远程按次计费 —— 而这是**每次检索**都要算一次查询向量的路，
  账单随使用量长。本地是一次性下载（约 600MB）之后零边际成本。落地照 `heavy_deps.py`
  那套（缓存 + 清单 + 首启下载 + 后台预取），**不进分发包**。
  ② **嵌入单位是「窗口」不是「切片」**：文档 §3.1 那条"粒度直接用切片"对 embedding 是错的 ——
  切片平均 **6979 字**、最长 36846 字，而模型可用窗口是 1024 token，

  ③ **模型选 bge-m3 而不是更小的 e5-small**：同一份考卷 top1 **8/8 vs 6/8**、

  代价 542MB（vs 112.8MB），已确认可接受。**它的 8192 token 卖点在 CPU 上不实用**：
  注意力是 O(seq²)，8192 配 padding 一次要 22GB（实测直接 OOM），实际能用 1024。
  ④ **固定走 CPU，不用 GPU**：本机有 RTX 5060，但**GPU 比 CPU 还慢**

  （CPU 版 10 倍）且要用户机器有匹配的 cuDNN，对"双击即用"不划算。
  落地时踩到一个真 bug：`is_ready()` 被**每次检索**调用，而它逐个文件算 sha256 ——
  601MB 一次 350ms（查询 367ms 里 350ms 花在这儿，真计算只要 14ms）。

  在模型眼里就是"这件事不存在"。现在没有切片可依时，保留它自己那一段的区间。
  现状与阻塞见 §八.6。
