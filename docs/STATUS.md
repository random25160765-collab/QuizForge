## 一、形态（一句话）

**对话是前台，题与图是后台。** 学习者在 `chat.html` 里问、被推题、就地作答；
判分与写回走的仍是刷题页那条路，掌握度 / SM2 / 收藏夹还是同一份记录。

## 九、最近的决策

- **2026-09-17** —— **学习前台换成对话**。三种零件（题卡 / 凭条 / 引用）都长在消息上，
  落库、可刷新、随分支切换。两条硬边界：写操作**只提案**，改状态的那一下永远是用户点的；
  掌握度**只从作答长出来**（不给工具任何直接改它的路子）。
- **2026-09-17** —— **三路召回落了前两路**：规则（字面检索 + 按行回读原文，引用与它同源）、
  图（从前置/后继/组成/易混四个方向走，邻居带掌握档位）。**向量仍不做** ——
  等“他换了个说法问同一件事”成为真问题再说，RRF 融合也等第三路。
- **2026-09-17** —— **工具循环的两条硬规矩**：历史里**回放**工具调用与结果
  （只回放文本会让模型学成“只说不动”，实测它会在调工具前停下）；轮数用尽时最后一轮
  **不给工具**，逼它把已经查到的东西说出来（否则用户只拿到一堆工具气泡、一个字结论都没有）。
  回放时单条工具输出夹到 700 字 —— 不夹的话第二轮 prompt 就会撞超时。
- **2026-09-16** —— **技术栈定案**：所有 LLM 能力走 API（chat / vision / embedding），
  **不引任何推理框架**（把 torch / transformers 那一整片挡在门外）；依赖判据是「重量」——
  体积、是否要起外部服务、传递依赖数，轻则引、重则手搓；三个接口（`LLMClient` /
  `VisionClient` / `Embedder`）都走 OpenAI 兼容、provider 只是配置；embedding 必须本地缓存
  （索引频繁重建）；账本按能力分别记。落地在 `pipeline.md` §7。
- **2026-09-16** —— 新增 skill **`quizforge-handmade`**（人工手写单题的接入）：agent 不写题面，
  只做格式合规、元数据补全、把关系边写成可解析的句式（前置/易混/迁移/锚定）、校验与入库 ——
  保证手写题（尤其法式大题）**不进图谱盲区**。已登记进 `skills/README.md` 与 `quizforge-init` 路由表。
- **2026-09-16** —— **编排定案**：出题 + 校验是一个**串联单元**（两个独立会话），**N 个单元并联**；
  L1–L4 一视同仁地并行（不给 L3/L4 单开串行轨）；**只有法式大题一题一议、不进流水线**（人做，
  但产物照常入库并参与关系解析）。「串联」指流程不指上下文 —— 校验员不看 `## 解析`。落地在 §6.5。
- **2026-09-16** —— 定下**先后顺序**：① 知识空间 → ② 检索层 → ③ 学习算法（含回流）→ ④ RAG / 问答。
  回流通道**不涉及语义理解**，硬编码一个实时算法即可（正确率 → 难度标定、错答共现 → 关系强度、
  IRT/BKT → 掌握度）。落地在 `references/pipeline.md`。
- **2026-09-16** —— 确立**宏观框架**：自动出题 ≙ 知识库构建流水线（清洗切分 → 标注 → 分类 → 学习），
  终点是一个「知识空间」（点 / 边 / 样本 / 坐标）；同时记下三处类比会破的地方
  （合成样本而非贴标签、闭环回流、验收标准是学习效果）。落地在 §0.5。
- **2026-09-16** —— 检索层与执行器定案：三路召回（向量语义 / 图逻辑关联 / 规则）+ **RRF 融合**；
  **出题即标注**（题库同时是标注数据集，喂给智适应与知识图谱）；并行调度**自建**（SQLite 任务表 +
  租约 + dispatcher/worker/verifier 三进程），不依赖第三方 agent 框架。落地在 §5 / §6。
