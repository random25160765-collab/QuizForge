# 设计说明

这份文档记录 quizforge 的**工程决策与取舍** —— 为什么这样设计、哪些坑踩过、
哪些地方看起来可以更简单但不该简化。使用说明见 [README](../README.md)。

---

## 一、两种形态共用一套运行时

在线版（FastAPI + PostgreSQL）与离线版（单文件 HTML）**界面与判分逻辑完全相同**，
差别只在两处：

| | 数据从哪来 | 数据往哪存 |
|---|---|---|
| 在线版 | `GET /api/bank` | `POST /api/progress/sync` |
| 离线版 | 构建期内联的 `window.__QB__` | 浏览器 localStorage |

做到这一点靠两个「接口不变」的收窄：

- `data.js` 的建索引逻辑包进 `QF.data.install(bank)`。离线时从 `window.__QB__` 灌入，
  在线时从接口灌入。**索引、主题树、筛选逻辑一行不改。**
- `store.js` 对外仍是**同步 API**（89 处调用点）。在线时启动拉一次快照灌进本地，
  之后所有读都是同步的本地读；写则落本地 + 入队异步回传。UI 层一行不改。

代价是要维护「服务端权威」与「本地乐观」两份状态的一致性，见第六节。

## 二、离线产物的取舍

**产物内联而不是 `fetch` 题库。** `file://` 下 `fetch`/XHR/ES module `import` 会被
CORS 拦截，只有普通 `<script src>` 与 `<link rel=stylesheet>` 能加载。所以题库在构建期
序列化成 `window.__QB__` 内联进 HTML。序列化时要转义 `</script`、`<!--`，
避免题面里的代码块把脚本截断。

**手写 Markdown 渲染器与语法高亮器**，不引入 marked / highlight.js。
题库 Markdown 是受控子集，自写反而能原生解决 LaTeX 与 Markdown 的语法冲突：
解析顺序被固定为「围栏代码块 → 数学公式 → 行内代码 → HTML 转义 → 行内标记 → 还原」，
所以 `$a_b$` 不会被下划线吃成斜体、`x^2` 不会被强调语法破坏。

**KaTeX 字体 base64 内联。** KaTeX 的 HTML 输出依赖字体文件，`file://` 下 CSS 里的
`url(fonts/...)` 行为不一致，只有 base64 才真正自包含。`vendor.py` 只保留 woff2 子集
并剥掉 woff/ttf 回退声明，把体积压到约 600 KB。

**样式用原生 CSS，没有用 Tailwind CDN。** 产物要求完全离线自包含，
任何 CDN 依赖都会让双击打开时样式丢失。

**输入过程中不整体重渲染。** 填空与大题小问的输入只更新状态、不改 DOM，
否则每敲一个字都会替换掉 `<input>`，导致焦点与光标位置丢失。
因此作答值从 DOM 实时汇总，提交按钮也不使用渲染期算出的 `disabled` 快照。

## 三、数据模型：JSONB payload + 提升列

**题目**：题目的权威表示就是 `tools/question_parser.py` 产出的那个 dict，
前端（以及离线产物）消费的也是同一份 JSON。拆成 options / answer / parts 若干张表
就多出一层「库表 ↔ 解析器」映射要维护，任何一侧改字段都会静默漂移。
所以 `questions.payload` 存**原样 JSON**（与文件构建路径逐字节一致），
真正需要查询的字段（type / topic / difficulty）提升为列并建索引。

**记录**：同样取舍，但被劈成了两半 —— 见第五节。

**退役而不是删除**：源里删掉的题目只置 `retired_at`。用户的做题记录挂在题目 id 上，
物理删除会让历史进度出现空洞，掌握度与错题本都会莫名其妙地少东西。

**为什么序列化函数只有一份**：`question_to_dict` 与 `build_dataset` 放在
`tools/question_parser.py` 与 `tools/dataset.py` 里，离线构建与在线导入器**共用**。
两边各写一份序列化，迟早会漂移成「离线版正常、在线版某块界面静静空掉」，
极难定位。这条契约由 `api/tests/test_bank.py::test_bank_payload_matches_offline_dataset`
锁住（断言接口返回与 `dist/data.json` 逐字节一致）。

## 四、进度同步：attempts 是计数的唯一来源

**问题**：早期实现让客户端上传记录对象（「我这台设备看到的累计值」），
多设备下按 `client_rev` 做 last-write-wins。一台设备离线作答后回传，
若它的 rev 已被另一台超过，这次作答就被**静默丢弃** —— 计数不增，用户毫无察觉。

**解法**：每次判分产生一条**流水**（增量），服务端只对**真正插入成功**的流水累加。

```python
pg_insert(Attempt).values(rows).on_conflict_do_nothing(
    index_elements=["id"]        # id 由客户端生成
).returning(...)                 # 只有返回的行才触发累加
```

「请求发出、响应丢了、客户端重发」在网络里是常态。把幂等交给主键约束，
再用 `RETURNING` 拿到实际落库的行，就不必写「查一下有没有、再决定加不加」——
那套逻辑在并发下本身就是错的。

**为什么选「增量累加」而不是「全量重算」**：

| | 全量重算 | 增量累加（选定） |
|---|---|---|
| 存量数据 | 没有对应流水，**会归零** | 原样保留，零迁移 |
| 跨设备正确性 | 正确 | 正确 |
| 代价 | — | 聚合逻辑日后若改动，无法靠重算历史修复 |

「存量数据不为零」比「历史可重算」重要得多。

**乱序到达**（离线设备补传旧流水）由 SQL 兜住：

- `first_at` 用 `CASE WHEN first_at = 0 THEN :at ELSE LEAST(...)`（初值是 0，直接 LEAST 会永远得 0）
- `last_status / last_score / last_response` 只在 `:at >= last_at` 时更新，
  否则补传旧数据会把「最近作答」改回过去，界面上的判定条会显示一个过期的答案

**日期归属由客户端决定**（`attempts.day`），不用服务端时区从 `at` 反推：
服务器跑 UTC 时，用户凌晨作答会被算到前一天，热力图与「今日已练」就对不上。

## 五、计数与补丁必须彻底分开

服务端**不再接受客户端上传的计数**，这条做成了硬约束（`sync_ops.COUNTER_INPUT_FIELDS`），
并在测试里断言。只要还允许上传计数，一台设备的快照就会覆盖另一台的增量，
等于问题没解决。

| 通道 | 字段 | 合并方式 |
|---|---|---|
| 计数 | attempts / correct / partial / wrong / first_at / last_at / last_status / last_score | 只由流水原子增量，**永不接受客户端上传** |
| 补丁 | sm2 / note / streak / parts / last_response / mastered / flagged | 按 `client_rev` 的 LWW |

几个具体取舍：

- **`streak` 放补丁通道**：它只参与掌握度的连对加成（上限 3 次），
  从流水推导需要按题额外查最近若干条并处理乱序，成本与收益不成比例。
  它会在下一次作答时自然纠正。
- **`lastResponse` 双源**：流水在更新时也写它（与 `lastStatus` 同步），
  补丁通道**也**能写它 —— 因为「待批改」那次提交（`ungraded`）**不产生流水**，
  只由流水驱动的字段装不下用户填的内容。两边同时写时值相同，不会冲突。
  最初把它整体移出流水，结果界面上出现了「判定说答对了、展示的却是另一个错答案」。
- **`records` 迁移必须保数据**：从「整份 payload」拆成「计数列 + 补丁列」的迁移
  （`20260915_0900_a1c4e0f27b93`）写成了 `ADD COLUMN` + 从现有 JSON 回填，
  **不能 drop table** ——表里已有真实计数。

## 六、快照合并：谁覆盖谁

`store.hydrate()` 有三处必须「合并」而不是「覆盖」的地方。直接覆盖的后果都真实发生过：

| 位置 | 直接覆盖的后果 | 正确做法 |
|---|---|---|
| 每日统计 | 新账号服务端返回空对象（真值），一登录就把本地热力图历史抹掉 | 逐字段取**较大值** |
| `settingsRev` | 服务端对设置是「rev 不大于已存值就拒绝」，本机 rev 被覆盖变小后，**之后每次设置变更都被静默拒绝** | 取**较大值**（Lamport 抬升） |
| 记录补丁 | 本地 rev 更大的记录是断网期间攒的改动，不能被旧的服务端数据盖掉 | 保留本地并标脏 |

为什么每日统计取 max 是安全的：流水的权威副本在服务端，本机的乐观值只多不少，
流水推上去之后服务端会追平并超过它，下一次合并自然收敛。

**每日统计在服务端是累加**（不是取 max）。两台设备同一天各练 10 题就是 20。
`topics` 的键是动态的，JSONB 没有「按路径自增」的原子写法，所以退化为
「`ON CONFLICT DO NOTHING` 确保行存在 → `SELECT ... FOR UPDATE` → 读改写」。
每日统计只占一行，开销可以忽略。

**重置与导入走独立的 `resets` 通道**：补丁是增减语义，表达不了「直接设成某个值」。
`resets` 直接设定计数，且**刻意不删流水** —— 流水是幂等键的载体，删掉之后客户端重发
一条旧流水就会重新插入并再累加一次，反而多算。代价是重置后
`records.attempts` 不再等于该题流水条数，这是本方案选择「增量累加」的必然结果。

**`daysSeed`**：导入备份带来的历史热力图没有流水支撑，
所以单独一条通道，且**按日期把关** —— 只接受「该用户在这一天还没有任何流水」的日期，
并取较大值（幂等）。于是从离线版迁移过来时历史完整保留，而已经有真实作答的日期
不会被伪造的数字盖掉。

## 七、掌握度：双端夹具锁一致性

前端要即时反馈（点完选项立刻看到掌握度变化），服务端要聚合统计，所以两边各有一份实现。
`meta/mastery-fixtures.json` 是它们共同的契约，`pytest` 与 `tools/selftest.mjs`
断言同一份数据。任一侧漂移立刻失败。

夹具里有两个**原始分恰好落在 .5 上**的用例专门盯取整差异：
JS 的 `Math.round` 向上（32.5 → 33），而 Python 内置 `round()` 是银行家舍入
（32.5 → **32**）。没有这两条，用 `round()` 也会「看起来正常」。

`api/app/mastery.py` 是规范实现，并显式用 `floor(x + 0.5)` 模拟 JS 的取整。

## 八、鉴权与路由契约

- **密码**：argon2id（`argon2-cffi`）。
- **会话**：32 字节随机串，Cookie 里放明文，**库里只存它的 sha256**，
  校验时查表比对。因此**不需要服务端签名密钥** —— 早期从 JWT 方案沿袭下来的
  `QF_SECRET_KEY` 是一条假需求（从未被读取过，却让运维多做一个无用步骤），已删除。
- **CSRF**：`SameSite=Lax` + 双提交令牌（Cookie 值必须等于请求头）。登录/注册这类
  尚未持有令牌的写请求，靠 `verify_same_origin` 防跨站登录。

**读接口与写接口用不同的依赖**，这是踩过三次的坑：

| 依赖 | 用途 | 含 CSRF 校验 |
|---|---|---|
| `CurrentUser` | 读接口 | 否 |
| `AuthenticatedWriter` | 写接口 | 是 |

混用会让浏览器发出的 `GET` 因为没有 CSRF 头而 403。
现在有一条 `test_route_contract.py` 遍历**全部路由表**兜住
（读接口不得挂 CSRF 依赖、写接口必须挂、路径统一在 `/api` 下、无重复注册），
新增接口自动纳入检查。

依赖放在同一个 `Depends` 里而不是路由级 `dependencies=[...]`：
路由级依赖先于参数依赖执行，匿名请求会拿到 403（CSRF 失败）而不是 401（未登录），
既误导前端，也等于告诉探测者服务端的状态。

## 九、AI 批改：每个用户自带密钥

服务端**不持有、也不提供任何共享密钥**。密钥来自调用者自己的
`user_settings.data.ai`，服务端只做「转发 + 带上下标人的密钥」。

为什么仍要过服务端？**纯粹是跨域**：不少模型供应商的接口不允许浏览器直连，
前端直发在浏览器里根本出不去。

服务端只保留三项与个人凭据无关的策略：`ai_enabled`（实例级总开关）、
`ai_daily_quota`（每人日限）、`ai_timeout_ms`（超时上限）。

**代价要说清楚**：密钥存在服务端数据库里（按用户隔离），数据库泄露会连带泄露
用户的密钥。这是「跨设备免重填」换来的。若哪天觉得不划算，退路是让浏览器把密钥
只留在本地、每次请求随头上送（服务端不落库），代价是每台设备都要重填一次。

服务端**不读** `config/ai.local.json`：那是离线单页时代用来内联进 HTML 的本机默认值，
现在只剩 `make build-local` 用得到（构建离线产物时注入），与在线服务端无关。

## 十、静态资源与缓存

**资源文件名不带内容哈希**（`/assets/runtime/app.js` 永远是同一个 URL），
所以缓存策略必须按「内容会不会变」分档，写在 `main.py` 的 `cache_policy` 中间件里：

| 路径 | 策略 | 理由 |
|---|---|---|
| `/assets/fonts/*.woff2` | `public, max-age=31536000, immutable` | 字体内容永不改变 |
| `/assets/*.js` `/assets/*.css` `*.html` | `no-cache` | 每次回来校验；配合 ETag 走 304，代价很小，但保证部署后立刻生效 |

不做这件事的后果真实踩过：Starlette 不主动发 `Cache-Control`，浏览器于是按
Last-Modified 做启发式缓存 —— 部署新版本后老用户会继续跑缓存里的旧 JS，
表现为「改了前端，刷新看不到」。

**镜像自包含**：Dockerfile 是多阶段的，前端产物在镜像内用
`tools/build_web.py` 生成，不依赖宿主先跑 `make web`。
之前靠 `./api/web:/app/web` 绑定挂载提供前端，而 `api/web` 在 `.gitignore` 里 ——
干净机器上部署时挂载目录是空的，页面直接白屏。

代价要说清楚：**去掉挂载之后，改前端必须重建镜像**（`docker compose up -d --build`），
`make web` 只写到宿主目录，进不到已经在跑的容器里。
所以本机改前端走 `make api-dev`（宿主 uvicorn + 热重载，直接读 `api/web`），
容器只用于「部署形态的验证」。

**密钥不进入任何产物**：`dist/` 是「可以对外发布」的目录，永远不含密钥；
`dist-local/` 是本机自用（`make build-local` 会把 `config/ai.local.json` 内联进去）。
两者刻意分开，避免误传。发布前可扫一遍：

```bash
grep -c '<密钥前缀>' dist/*.html    # 期望全为 0
```

## 十一、运行环境

| 部分 | 要求 |
|---|---|
| 出题 / 构建 / 导入器 | Python 3.12+，PyYAML（只依赖标准库 + PyYAML） |
| 在线后端 | Python 3.12+（容器内为 `python:3.12-slim`）、PostgreSQL 16 |
| 前端 | **不需要 Node**（`selftest.mjs` 是唯一用 Node 的脚本，用于跑测试） |
| 容器 | Docker + Docker Compose |

**前端不引入 npm、不引入打包器**，运行时是手写 JS 按固定顺序拼接。
新增运行时脚本时要在 `tools/build.py`（离线）与 `tools/build_web.py`（在线）的
`RUNTIME_ORDER` 里都登记 —— 顺序错会导致引用未定义的模块。

## 十二、Agent 扩展

仓库自带两个便于交给 agent 的能力：

- **`quizforge-author` skill**：规定题目文件位置、front-matter 字段、
  五种题型的正文小节契约、LaTeX 与代码块写法、代码填空与法式大题的写法，
  以及新增后必须执行的校验命令。触发语见 README 的「出题」。
- **`make test`**：题库校验 + 前端逻辑自测（判分 / 渲染 / SM2 / 掌握度 / 持久化 /
  流水与快照合并口径）。改判分或数据口径时先跑它。

## 十三、已知局限

- **`streak` 不在服务端推导**：它随补丁通道走 LWW。理论上两台设备并发作答时，
  连对次数可能短暂不一致；下一次作答会纠正。它的影响面仅限于掌握度的 +9 分加成。
- **`resets` 之后计数与流水条数不再对应**：见第六节。这是「增量累加」的必然结果，
  不是 bug；但如果将来要做「从流水重算」的功能，需要先补一张基线表。
- **`attempts` 的 `id` 是全局主键**：理论上两个用户生成同一个 UUID 会撞
  （v4 碰撞概率可忽略）。日后若要更严谨，可以改成 `(user_id, id)` 复合主键。
- **没有找回密码**：未做邮箱验证，刻意如此。密码丢失只能靠 `make db-backup` 的备份恢复数据。
