# 出题流水线：从材料到题库

`from-source.md` 是**单批**流程（几道题，一个会话能做完）。本文件是**批量**流程：
面对一本书、一套手册、几百篇论文时按这里走。规模分界线大致是
「材料超过一个会话能装下的量，或者题量以十为单位以上」。

## 0. 总览

```
材料(只读) → 切片索引(可重建) → 覆盖矩阵(知识点) → 并行出题 → 独立校验 → 统合归类入库
                                      ↑                                  ↓
                                      └─── relations.yaml ←── 题目字段自动解析出边
```

三条不变量：

1. **题目是事实，索引是投影。** `questions/*.md` 是唯一事实来源；切片与矩阵都可重建，
   **永不反向覆盖题目**。在线库同样是投影（`import_bank` 单向导入）。
2. **先出题，最后归类。** 考纲（`meta/topics.yaml`）只作归类依据、可随时重构；
   绝不为填考纲出题，也不因考纲没有合适的 key 就不出题。
3. **产出按知识点打包，不按材料切片打包。** 切片只是读材料的手段，知识点才是产出单位。
   这一条是并行不重复的前提。

## 1. 批次分三类，不按比例分

**题量是材料的函数（覆盖率下限），不是预算。** 铺满知识点后 L1/L2 占大头是**结果**，
不要预先规定 L1:L2:L3:L4 = 14:8:1:1 这类比例。

| 类 | 内容 | 目标 | 并行性 |
|---|---|---|---|
| **A 覆盖批** | L1 + L2 合并，`single`/`multi`/`blank` | 知识点**出满**：每点至少 1 道，重点 2–3 道 | 大规模扇出 |
| **B 精修批** | `short` + `problem`（L3/L4） | 顶级难度，一道一议、单独出单独审 | **串行** |
| **C 统合** | 去重、归类、改考纲、入库 | 全局一致 | 单 agent，串行 |

经验密度：**顶级题约 50 页 1 道**（大量知识点堆叠的那种）。其余都归 A 类。
重复容忍度：**3 道以内重复不干预**，对账只看覆盖率、不看重复率。

## 2. 五步

### ① 切片：按结构切，不按长度切

切的是**结构**；允许切得不完美，合并阶段会修。唯一不可妥协的是**出处坐标**。

| 材料形态 | 切片依据 | 做法 | 陷阱 |
|---|---|---|---|
| Markdown / 文档站 | 标题层级 | `grep -nE '^#{1,3} '` 出大纲 → 按标题区间切 | — |
| 手册 / 规范 PDF | 目录树 + 小节编号 | 提 outline，再用编号正则 `^\d+(\.\d+)*\s` 定小节起点 | 页眉页脚与跨页表格污染文本，先清 |
| 论文 PDF | 固定 IMRaD 骨架 | Abstract / Intro / Method / Evaluation / Conclusion 一级切，节内按编号二级切；**References 与附录丢掉** | 双栏排版会让左右栏文本交错；引用编号 `[12]` 混进句子 |
| 大部头教科书 | 章 → 节 | 先按章粗切，章内按小节细切 | 几百页必须两遍 |
| 扫描版 PDF | 必须先 OCR | OCR → 回到手册档 | 无文本层时 outline 也是空的 |
| 源码仓库 | 模块 / 头文件 / 函数 | 头文件给公共 API；`git log` 顺带给出演化顺序 | 别把整个仓库当一个切片 |
| 笔记堆 / 聊天记录 | 先归一，再切 | 先把碎片并成主题、去重 | 时间戳与口语噪音 |

**四条纪律：**

- **双坐标**：每片记「结构路径（`第3章 › 3.2 › 3.2.1`）」+「物理坐标」。
  **PDF 用页码，不要用全局行号**——换一个转换工具行号就全变了，而 `source` 字段要长期悬在那里。
- **重叠窗口**：边界留 1–2 段重叠，防止知识点被切断；重复在合并阶段自动消掉。
- **主题纯度自检**：一片要能一句话说出"它在讲什么"。说不出、或装了 3 个主题 → 切太粗；
  只有一两句 → 切太碎，并进邻居。
- **骨架先行**：材料越乱，越要先产出目录树**给人过一眼**再切。边界歧义只有人能一票定，
  agent 猜一百次也不准。**这是整条流水线上唯一必须人介入的地方。**

目标尺寸 4–8k tokens（约 6–12 页、或论文的一节），但**宁可一片 12k，也不要切在句子中间**。
这一步基本不用 LLM（PDF 用 `pdftotext` + outline，MD 用 grep），可全量跑，近乎免费。

### ② 逐片抽取知识点（唯一必须用 LLM 的一步，可按片并行）

每片跑一次，产出**结构化列表**（不要自由文本，否则无法合并）：

```yaml
- key: ptx-state-space          # 稳定标识，用材料里的英文术语小写化
  name: PTX 状态空间
  source: [ptx_isa_9.3.pdf, 87]  # 文件 + 页/行区间（可多个）
  kind: noun                     # noun | api | number | invariant
  thickness: 3                   # 1..3，材料给了多少可考事实
  layers: [识记, 理解]
  terms: [.global, .shared, .const]
  requires: []                   # 留空，由 relations 解析回填
```

### ③ 合并归一（串行）

- **合并**：同一个点被多片抽到 → 出处取并集；同义不同名（`L1` / `SRAM` / `local SRAM`）→ 合并并记别名。
- **拆分**：`thickness ≥ 3` 的大点要拆（"三 kernel 模型"拆成 reader / compute / writer + CB 四个点）。
- **归组定标**：按章节层级归两层，标优先级与可考层。
- **顺手产出考纲 diff**：矩阵里有、`topics.yaml` 里没有的 → 这是"最后改考纲"的输入清单，不用另做分析。

产出即**覆盖矩阵本体**。

**粒度用一句话检验：**

> **"哪道题算覆盖了它？"——答不出来，粒度就是错的。**

**一条硬规则：没有出处的知识点直接删掉。** 那说明它是凭印象写的。

### ④ 按知识点打包出题任务

一个任务包 = 3–6 个知识点 + **它们各自的原文段落**（带坐标，不是整片）+ 契约 + 当前已出题清单。
只带相关段落这一步很关键：省 token，并且几乎消除跨任务重复。

任务 id 用「材料切片哈希 + 知识点 key」定，重跑只补缺口（幂等）。

### ⑤ 覆盖率对账（C 类前）

用矩阵逐点核对："这个知识点有没有题？" → 缺口列表 → 补出。
**对账看覆盖率，不看重复率。**

## 3. 存储：三层文件，存坐标不存正文

```
maps/
└── <材料名>/                      # 按「材料」分目录，不按学科
    ├── slices.yaml               # 切片索引（可重建）
    ├── coverage.yaml             # 覆盖矩阵（知识点）
    └── relations.yaml            # 关系边（从题目解析生成，不是手写）
```

**两类派生资产分开放**：`maps/` 放机器生成的索引与矩阵（可重建，删了能重跑）；
`draft/` 放人写的母本与草稿（如 `draft/<材料名>.master.md`）。
母本是地图，值得留着，但**不当作一道题交付**。

- **不存正文，存坐标 + 一句话摘要。** 正文从材料现取（材料通常在仓库外，只读）。
  摘要那行是为了"换台机器也能看懂矩阵"——与 `source` 字段同样的哲学：人类可读线索，不做机器核对。
- **按材料分目录，以知识点 `key` 作为跨材料连接键。** 同一个 `ptx-state-space` 出现在手册与指南里，
  就是两条 `slices` 记录挂在同一个 key 下——跨材料对齐**不需要额外机制**。
- **用文件，不用数据库（现在）。** 规模是几十 MB 的文本，而查询模式还没稳定；
  更重要的是项目已经定了"源在 git、库是投影"。升级判据：

| 触发信号 | 上什么 |
|---|---|
| 多表 join 查询变成日常（如"哪些知识点没题且被前置依赖"） | SQLite |
| 单文件几万行、diff 噪音盖过价值 | SQLite + 视图 |
| 真需要图算法（最短学习路径、社区发现） | 图数据库 |

**几千个点用不着图数据库**——递归 CTE 就够；图库的价值在百万级边。

## 4. 关系不靠标注，靠解析

**不要在切片时标注关系**：切片是结构操作（零成本、可全量、确定），关系是语义判断
（要理解、成本高），而且此刻你还不知道哪些关系有用。
**在信息最少的时候做最贵的判断**，和"先出题最后归类"是同一个错误。

现有契约里的字段**本来就已经是图的边**：

| 已有产出 | 自动得到的关系 |
|---|---|
| `### 选项辨析`（"什么人会选它"） | **易混边**：正确答案 ↔ 干扰项 |
| `problem` 的小问复用（"可引用第 N 问的结果"） | **前置边**：问 i → 问 j，带顺序（母本的骨架） |
| `layer: 迁移` 题的迁移锚点一句话 | **迁移边**：原理知识点 → 新情境知识点 |
| 每题的 `source` | **锚定边**：知识点 → 材料段落 |
| 做题记录（错答模式、掌握度变化） | **前置边/强度**：数据反推 |

所以只需要一个解析脚本（`tools/relations.py`，待建）：扫 `questions/` 全量，把这些字段抽成
`relations.yaml`。**零额外标注劳动**，题目变则图变。
只在"某条前置关系任何题里都没有线索"时人工补一条，按需补、不预先铺。

## 5. 为什么不用向量库

- **切片靠结构，不靠语义相似。** 语义切分会把结构丢掉，而且**不可复现**——同一份材料两次切出不同的片，
  覆盖矩阵就没法对账。
- **矩阵要的是「知识点 → 精确页/行区间」的硬映射**，向量检索给的是"大概相关"，方向正好相反。
- **去重不需要它**：已决定 3 道以内重复不干预。
- **关系需要的是图，不是向量**：向量距离是对称的、只表示"像不像"；而前置关系是**反对称的**
  （A 是 B 的前提，反之不成立）。用向量保留关系在概念上就不成立。
- **智适应不需要它**：自适应 = 按每题结果更新知识点掌握度再选题，这是 IRT/掌握度追踪 + 排程，
  项目里已有 `mastery.py` + SM2 + 错题本。真正缺的只是**前置约束**
  （选 B 的题之前，若 A 未掌握就先补 A），只需覆盖矩阵的 `requires` 边，零新基础设施。

向量库唯一有价值的位置是**段落级检索**（做错题后把材料里相关几段捞回来复习）——那是辅助功能，
不进主链路，等项目真的需要再加。

## 6. 执行与成本

**并行/串行分工**：A 类扇出、B 类串行、C 类单 agent。
无论用哪个环境，三条硬约束不变：一个任务包一个任务；契约与输出骨架同一份；
**校验必须是独立会话**（另一个 agent、重读原文、**不看作者的解析**，否则会被带偏）。

CodeBuddy 不支持扇出 → 在这个环境里跑就是串行版（同一会话复用契约可以省 token，但慢一个量级）；
需要并行时用支持扇出的工具。

**量级估算**（一本书：30 万 tokens、约 120 道、顶级题约 6 道）：

| 阶段 | 并行耗时 | 串行耗时 |
|---|---|---|
| 覆盖矩阵 | ~5 min | ~5 min |
| A 覆盖批 | ~22 min | ~3.8 h |
| 独立校验 | ~14 min | ~2.3 h |
| B 精修批（6 道） | ~1.5 h（可与前两段重叠） | ~1.5 h |
| 统合入库 | ~20 min | ~20 min |
| **合计** | **≈ 2 h wall clock** | **≈ 8 h（实际因会话往返更久）** |

Tokens ≈ 3M（便宜档约 $1、贵档约 $15）。人工 ≈ 2 h：A 类抽检 20 min + **顶级题精审 6×15 min** +
过考纲 30 min。

**结论：钱可以忽略，人的时间是瓶颈，而且瓶颈集中在顶级题的精审上。**
所以 A 类可以放心出满，顶级题要克制——每一道都实实在在花掉用户 15 分钟。
