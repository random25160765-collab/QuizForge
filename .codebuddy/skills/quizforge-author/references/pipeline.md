# 出题流水线：从材料到题库

`from-source.md` 是**单批**流程（几道题，一个会话能做完）。本文件是**批量**流程：
面对一本书、一套手册、几百篇论文时按这里走。规模分界线大致是
「材料超过一个会话能装下的量，或者题量以十为单位以上」。

## 0. 总览

```
材料(只读) → 切片索引(可重建) → 覆盖矩阵(知识点) → 并行出题 → 独立校验 → 统合归类入库
                                      ↑                                  ↓
                                      └─── relations.yaml ←── 题目字段自动解析出边
```

三条不变量：

1. **题目是事实，索引是投影。** `questions/*.md` 是唯一事实来源；切片与矩阵都可重建，
   **永不反向覆盖题目**。在线库同样是投影（`import_bank` 单向导入）。
2. **先出题，最后归类。** 考纲（`meta/topics.yaml`）只作归类依据、可随时重构；
   绝不为填考纲出题，也不因考纲没有合适的 key 就不出题。
3. **产出按知识点打包，不按材料切片打包。** 切片只是读材料的手段，知识点才是产出单位。
   这一条是并行不重复的前提。

## 0.5 宏观框架：三个阶段，一个产物

自动出题和数据处理是同构的——更准确地说，它是一条**知识库构建流水线**：

| 阶段 | 数据处理 / KG 构建里的对应物 | 这里做什么 | 产物 | 落在哪 |
|---|---|---|---|---|
| **清洗切分** | 分块 + 去噪 | 按结构切；清页眉页脚与引用编号；图按原位钉住 | 切片索引（结构坐标 + 物理坐标 + 图占位符） | `maps/<材料>/slices.yaml` |
| **标注** | 合成样本 + 标注 | **出题**——题目本身就是标签载体（知识点 key / layer / 干扰源 / 迁移锚点 / `source`） | 题目（样本 + 全部标签） | `questions/**/*.md` |
| **分类** | 实体消解 + 关系抽取 + 本体对齐 | 知识点归并、关系出边、与考纲对齐 | 覆盖矩阵 + 关系边 | `coverage.yaml`、`relations.yaml` |
| **学习** | 特征 + 检索 + 排序 | 三路召回 + RRF，选出"下一个最该做的样本" | 检索接口 | `Retriever`（§5） |
| （回流） | 反馈闭环 | 做题数据修正难度、关系强度与覆盖 | **待建** | — |

**终点不是数据，是一个「知识空间」**，它有四样东西：

- **点**：知识点（稳定 key + 名称 + 材料出处 + `kind` + `thickness` + 可考层）
- **边**：前置（反对称、可传递）· 易混（对称）· 迁移（有向）· 锚定（指向材料）
- **样本**：题目——挂在点上的观测，带答案 / 评分要点 / 难度
- **坐标**：人在每个点上的掌握度与到期时间（SM2）

于是「学习算法」要解的问题变得很具体：**在知识空间上，给定当前状态与目标，选下一个最有价值的样本。**
可算的质量指标也随之有了：点的覆盖度、边的利用率、前置链的可达性。

**但这个类比有三处会破，设计时必须记住：**

1. **标注是「生产新样本」，不是「给旧数据贴标签」。** 所以它更像**合成数据生成**：
   标注流水线可以抽样质检，合成本必须整体可控——**每一道题都可能是错的**，
   这就是为什么独立的 `verifier` 是核心部件而不是可选项（§2 ⑤）。
2. **它是闭环，但回流这一环不涉及语义理解。** 做题数据回来修正标注：正确率 → 难度标定；
   错答共现 → 关系强度；IRT / BKT → 掌握度更新。**这些全是可硬编码的实时算法**，不需要 LLM，
   也不属于这条流水线。**当前不设计它**——先把知识空间做扎实，后面的学习算法乃至 RAG 才有东西可做。
3. **终点函数不同。** 数据处理的终点是"特征好用"；这里的终点是"人的能力增长"。
   覆盖率是必要条件，但**验收标准是学习效果**（掌握度变化、审读命中率），不是数据指标。

**先后顺序是硬的**：

```
① 知识空间（清洗切分 → 标注 → 分类） → ② 检索层（三路召回 + RRF）
   → ③ 学习算法（含回流，硬编码实时更新） → ④ RAG / 问答
```

前一步不扎实，后一步就没有东西可做。所以本文的重点是 ①②；③④ **只定接口、不实现**。

## 1. 一条流水线，四层共用

**四层不分批。** 任务按**知识点**打包，一个包里每个点按各自 `layers` 出题：
含识记/理解就出 `single`/`multi`/`blank`，含应用/迁移就出 `problem`/`short`。
层是**内容维度**（题怎么写、怎么判定），不是**流程维度**——不存在「先覆盖批、再精修批」。

四个阶段固定，且覆盖题与精修题在队列里**没有区别**：

| 阶段 | 做什么 | 并行性 |
|---|---|---|
| ① 派工 | 按知识点打包（每包 3–6 个点 + 各自原文段落） | 单发 |
| ② 出题 | 一次把该点各层该出的都出了 | 大规模扇出 |
| ③ 独立校验 | 换会话、重读原文、不看作者解析；不合格带缺陷清单重出 | 大规模扇出 |
| ④ 统合入库 | 去重、topic 归一、改考纲、提升进正式题库 | 单发 |

**题量是材料的函数（覆盖率下限），不是预算**：不要预先规定 L1:L2:L3:L4 的比例，
L1/L2 占大头是**结果**而不是计划。
重复容忍度：**3 道以内重复不干预**，对账只看覆盖率、不看重复率。

## 2. 五步

### ① 切片：按结构切，不按长度切

切的是**结构**；允许切得不完美，合并阶段会修。唯一不可妥协的是**出处坐标**。

| 材料形态 | 切片依据 | 做法 | 陷阱 |
|---|---|---|---|
| Markdown / 文档站 | 标题层级 | `grep -nE '^#{1,3} '` 出大纲 → 按标题区间切 | — |
| 手册 / 规范 PDF | 目录树 + 小节编号 | 提 outline，再用编号正则 `^\d+(\.\d+)*\s` 定小节起点 | 页眉页脚与跨页表格污染文本，先清 |
| 论文 PDF | 固定 IMRaD 骨架 | Abstract / Intro / Method / Evaluation / Conclusion 一级切，节内按编号二级切；**References 与附录丢掉** | 双栏排版会让左右栏文本交错；引用编号 `[12]` 混进句子 |
| 大部头教科书 | 章 → 节 | 先按章粗切，章内按小节细切 | 几百页必须两遍 |
| 扫描版 PDF | 必须先 OCR | OCR → 回到手册档 | 无文本层时 outline 也是空的 |
| 源码仓库 | 模块 / 头文件 / 函数 | 头文件给公共 API；`git log` 顺带给出演化顺序 | 别把整个仓库当一个切片 |
| 笔记堆 / 聊天记录 | 先归一，再切 | 先把碎片并成主题、去重 | 时间戳与口语噪音 |
| 图文混排的 Markdown / HTML（tech report、教程） | 标题层级 + 图的位置 | 切文本时用占位符把每张图**钉在原位置**，图的清单另落 `figures.yaml` | 正文常以「见下图」当作解释主体，丢图就断了因果链 |
| PPT / 图文并重的报告 | 一页一片 | 每页当一个切片：该页文本 + 该页所有图 | 图是主体，纯文本切片几乎没有信息 |

**图文混排：图片是一等公民，不许丢。**

- **切片里保留图的位置**：文本视图中插入占位符 `[[图: 相对路径 | 说明: <alt / 图题>]]`，
  位置必须留在原处——图出现在哪一段之后，就意味着它解释哪一段。
- **每张图单独记账**（`figures.yaml`）：路径 · 出处坐标 · 说明文字 · 前后那句引用
  （「the following image shows …」）· 是否被正文当作解释主体 · 关联知识点 key。
- **视觉理解先筛后做**：只有「被正文当作解释主体」的图才值得过视觉模型（块图 / 架构图 /
  数据流图 / 时序图 / 曲线）；装饰性 logo、界面截图边角直接跳过。初筛用启发式（正文是否引用它 +
  所在目录 + 尺寸），再由抽取阶段确认。**这一步是整条流水线上唯一需要多模态的地方。**
- **图可以是知识点本身**：`kind: figure`。例：一张 Tensix 块图里，「5 个核 + 2 个 NoC +
  SFPU/FPU + packer/unpacker 谁连着谁」就是可考事实，而且**往往是正文没明写的**。
  出处坐标 = 图片路径 + 所在小节。
- **图怎么进仓库：让多模态模型「重绘」，不拷原图。** 材料是仓库外的只读软链，题目不能依赖它；
  而把第三方资料的图拷进**公开**仓库等于二次分发，有版权风险。按这个顺序选：
  ① **转写成文字 / 表格**（能讲清就不必画）；② **重绘**（**首选**：让多模态模型读图后产出
  **SVG / mermaid / graphviz** —— 可 diff、可编辑、体积极小，而且渲染器本来就支持代码块；
  结构是事实、画法是新的，版权干净）；③ 确实必须用原图时，先确认该材料可再分发、或把仓库转为
  私有，再拷到 `assets/figures/<材料>/`（webp/png，控制尺寸）。
  题目用 `![说明](assets/figures/…)` 引用，**alt 必须写全**。
- **结构图不要用文生图模型画。** 块图 / 数据流图 / 连线图里「谁连谁、箭头朝哪」正是考点，
  文生图会画错连线 ✗。要画就画成**代码**：模型读图 → 产出 SVG / mermaid / graphviz / TikZ → 渲染；
  代码能人工改一行、能 diff、评审时看得清改了什么。位图只在「必须保留原貌」时才用。
  重绘还有额外收益：**能把它重画出来，就说明真读懂了那张图。**
- **图有两种进题方式，通常两个都要**：题目**引用图**（考「能不能读懂图」），
  解析里**转写关键结构**（考「能不能说出图上有什么」）。这样答案才可核对、AI 批改才有依据。
  别忘了给 `![…]` 写全 alt 文本。

**四条纪律：**

- **双坐标**：每片记「结构路径（`第3章 › 3.2 › 3.2.1`）」+「物理坐标」。
  **PDF 用页码，不要用全局行号**——换一个转换工具行号就全变了，而 `source` 字段要长期悬在那里。
- **重叠窗口**：边界留 1–2 段重叠，防止知识点被切断；重复在合并阶段自动消掉。
- **主题纯度自检**：一片要能一句话说出"它在讲什么"。说不出、或装了 3 个主题 → 切太粗；
  只有一两句 → 切太碎，并进邻居。
- **骨架先行**：材料越乱，越要先产出目录树**给人过一眼**再切。边界歧义只有人能一票定，
  agent 猜一百次也不准。**这是整条流水线上唯一必须人介入的地方。**

目标尺寸 4–8k tokens（约 6–12 页、或论文的一节），但**宁可一片 12k，也不要切在句子中间**。
这一步基本不用 LLM（PDF 用 `pdftotext` + outline，MD 用 grep），可全量跑，近乎免费。

### ② 逐片抽取知识点（唯一必须用 LLM 的一步，可按片并行）

每片跑一次，产出**结构化列表**（不要自由文本，否则无法合并）：

```yaml
- key: ptx-state-space          # 稳定标识，用材料里的英文术语小写化
  name: PTX 状态空间
  source: [ptx_isa_9.3.pdf, 87]  # 文件 + 页/行区间（可多个）
  kind: noun                     # noun | api | number | invariant
  thickness: 3                   # 1..3，材料给了多少可考事实
  layers: [识记, 理解]
  terms: [.global, .shared, .const]
  requires: []                   # 留空，由 relations 解析回填
```

### ③ 合并归一（串行）

- **合并**：同一个点被多片抽到 → 出处取并集；同义不同名（`L1` / `SRAM` / `local SRAM`）→ 合并并记别名。
- **拆分**：`thickness ≥ 3` 的大点要拆（"三 kernel 模型"拆成 reader / compute / writer + CB 四个点）。
- **归组定标**：按章节层级归两层，标优先级与可考层。
- **顺手产出考纲 diff**：矩阵里有、`topics.yaml` 里没有的 → 这是"最后改考纲"的输入清单，不用另做分析。

产出即**覆盖矩阵本体**。

**粒度用一句话检验：**

> **"哪道题算覆盖了它？"——答不出来，粒度就是错的。**

**一条硬规则：没有出处的知识点直接删掉。** 那说明它是凭印象写的。

### ④ 按知识点打包出题任务

一个任务包 = 3–6 个知识点 + **它们各自的原文段落**（带坐标，不是整片）+ 契约 + 当前已出题清单。
只带相关段落这一步很关键：省 token，并且几乎消除跨任务重复。

任务 id 用「材料切片哈希 + 知识点 key」定，重跑只补缺口（幂等）。

### ⑤ 覆盖率对账（C 类前）

用矩阵逐点核对："这个知识点有没有题？" → 缺口列表 → 补出。
**对账看覆盖率，不看重复率。**

## 3. 存储：三层文件，存坐标不存正文

```
maps/
└── <材料名>/                      # 按「材料」分目录，不按学科
    ├── slices.yaml               # 切片索引（可重建）
    ├── coverage.yaml             # 覆盖矩阵（知识点，含 kind: figure）
    ├── figures.yaml              # 图片清单（路径 / 出处 / 说明 / 是否值得考 / 关联知识点）
    └── relations.yaml            # 关系边（从题目解析生成，不是手写）

assets/figures/<材料>/            # 拷进仓库的图，题目与解析引用它（不是所有图都拷，只拷用到的）
```

**两类资产分开放**：`maps/` 放机器生成的索引与矩阵（可重建，删了能重跑）；
`draft/` 放人写的手写题与草稿（`.codebuddy/skills/quizforge-handmade` 管这一类）。

- **不存正文，存坐标 + 一句话摘要。** 正文从材料现取（材料通常在仓库外，只读）。
  摘要那行是为了"换台机器也能看懂矩阵"——与 `source` 字段同样的哲学：人类可读线索，不做机器核对。
- **按材料分目录，以知识点 `key` 作为跨材料连接键。** 同一个 `ptx-state-space` 出现在手册与指南里，
  就是两条 `slices` 记录挂在同一个 key 下——跨材料对齐**不需要额外机制**。
- **用文件，不用数据库（现在）。** 规模是几十 MB 的文本，而查询模式还没稳定；
  更重要的是项目已经定了"源在 git、库是投影"。升级判据：

| 触发信号 | 上什么 |
|---|---|
| 多表 join 查询变成日常（如"哪些知识点没题且被前置依赖"） | SQLite |
| 单文件几万行、diff 噪音盖过价值 | SQLite + 视图 |
| 真需要图算法（最短学习路径、社区发现） | 图数据库 |

**几千个点用不着图数据库**——递归 CTE 就够；图库的价值在百万级边。

## 4. 关系不靠标注，靠解析

**不要在切片时标注关系**：切片是结构操作（零成本、可全量、确定），关系是语义判断
（要理解、成本高），而且此刻你还不知道哪些关系有用。
**在信息最少的时候做最贵的判断**，和"先出题最后归类"是同一个错误。

现有契约里的字段**本来就已经是图的边**：

| 已有产出 | 自动得到的关系 |
|---|---|
| `### 选项辨析`（"什么人会选它"） | **易混边**：正确答案 ↔ 干扰项 |
| `problem` 的小问复用（"可引用第 N 问的结果"） | **前置边**：问 i → 问 j，带顺序 |
| `layer: 迁移` 题的迁移锚点一句话 | **迁移边**：原理知识点 → 新情境知识点 |
| 每题的 `source` | **锚定边**：知识点 → 材料段落 |
| 做题记录（错答模式、掌握度变化） | **前置边/强度**：数据反推 |

所以只需要一个解析脚本（`tools/relations.py`，待建）：扫 `questions/` 全量，把这些字段抽成
`relations.yaml`。**零额外标注劳动**，题目变则图变。
只在"某条前置关系任何题里都没有线索"时人工补一条，按需补、不预先铺。

## 5. 检索层：向量 + 图 + RRF（多路召回）

**先明确一件事：流水线的产物不只是题库，而是一份结构化标注数据。**
出题过程本身就是理解过程——每道题都产出题目 / 答案 / 评分要点 / `source` 锚点 / 干扰项及其混淆源 /
迁移锚点 / 小问依赖。这些字段**同时也是**：知识图谱的边、检索的索引、智适应的观测值。
所以「标注」不是额外工序，它是出题的副产品（和 §4 是同一个逻辑）。

数据一旦有了，检索就是标准工程。这里定**三路召回 + RRF 融合**：

| 召回路 | 负责 | 强在哪 / 弱在哪 |
|---|---|---|
| **向量（Embedding）** | 语义相似：材料段落 ↔ 知识点 ↔ 题目 | 召回高、容忍措辞差异；但只表示"像不像"，没有方向 |
| **图（逻辑关联）** | `requires` 前置、`pairs` 易混、`used_by` 迁移，1–2 跳邻居 | 精确、有方向（前置是**反对称**的）；但召回低，找不到"没连过的东西" |
| **规则 / 元数据** | 同 topic、同 layer、掌握度阈值、SM2 到期、难度 | 完全确定、可解释；但不理解语义 |

**用 RRF（Reciprocal Rank Fusion，Cormack et al. 2009）融合**：
`score(d) = Σ_r 1 / (k + rank_r(d))`，k 取 60（原论文经验值）。

**为什么必须 RRF 而不是加权求和**：三路的分数**尺度根本不同**——余弦相似度、图的跳数、
规则的布尔值，归一化会引入一堆主观参数。RRF 只用**排名**，天然免归一化。这正是它当年被提出的原因。

**一个典型查询**（做错一道 CB 方向的题，下一步推什么）：

1. 向量：语义上最接近的材料段落与题目
2. 图：该知识点的 `requires` 前置（未掌握就先补）+ `pairs` 易混对（防混淆）
3. 规则：同 topic、layer 匹配、SM2 到期
4. → RRF 融合 → top-N → 交给选题策略

**分阶段落地**（架构现在就定，选型往后放）：

| 阶段 | 向量 | 图 | 要做的事 |
|---|---|---|---|
| 现在 | numpy 暴力余弦（几万条向量 < 10 ms） | SQLite 邻接表 + 递归 CTE | 定出 `Retriever` 接口，三路召回 + RRF + 评测集 |
| 量级上来 | pgvector / 专用向量库 | 图数据库 | 换实现，不动接口 |

**三条不能破的约束**：

1. **向量库与图库都是派生索引，不是事实来源。** 输入永远是 `questions/*.md` + `maps/*.yaml`，
   随时能重建（`reindex`）。绝不允许"只有索引里有、源文件里没有"的知识。
2. **切片与覆盖矩阵仍然结构化、确定性**（§2）：语义切分不可复现，覆盖矩阵要精确出处。
3. **前置关系走图，不走向量**：向量距离对称，前置反对称。三路是**互补**，不是互相替代。

## 6. 自建执行器（不用第三方 agent 框架）

这条流水线本质是一个 agent 应用，但**任务边界很清楚**（一个知识点包 = 一个任务），
用不着通用编排框架；而且 prompt、模型、成本、重跑策略都要自己控。

最小可用的形状，四个机制：

**① 任务表**（SQLite）：

```sql
tasks(id, kind, input_hash, payload_json, status, attempts, lease_until,
      result_ref, cost_tokens, started_at, finished_at, error)
```

`input_hash = 材料切片哈希 + 知识点 key`（§2 ④）→ **幂等**：重跑只补缺口，已完成的不重做。
`kind` 区分 `extract` / `author` / `verify` / `link`。

**② 三种进程**：

- **dispatcher**：读覆盖矩阵生成任务（按**缺口**生成，不按材料顺序），写进任务表
- **worker**：认领一个任务 → 调 LLM → 写结果文件 → 更新状态
- **verifier**：另一种 worker（`kind=verify`），**独立会话、重读原文、不看作者解析**（§2 ⑤）

**③ 租约而不是锁**：认领时写 `lease_until`，worker 崩了租约过期、任务自动回收，不会卡死。
`attempts` 超限的进 `dead` 队列，人工看一眼。

**④ 限流与账本**：并发上限、token 预算、429 退避；每个任务的 tokens / 耗时 / 成败落表——
这张表**就是** §7 成本估算的来源，也是"钱能算清"的根据。

技术栈与仓库一致：Python + SQLite + 线程/协程池，放在 `pipeline/` 下，与 `tools/`、`api/` 平级。
不引编排框架不是为了造轮子，而是**任务边界已经足够清楚，框架只会多一层不可控**。

## 6.5 编排：角色与交接

**原则：文件即接口。** agent 之间只通过文件交接（`maps/*.yaml`、`questions/*.md`、任务表的一行），
**对话历史不进交接**。理由：可审计（错在哪一步看得见）、可重跑（重放不必复现历史）、可 diff。

### 角色

| 阶段 | 角色 | 输入 | 输出 | 并行 |
|---|---|---|---|---|
| ① 切片 | **切片脚本**（非 agent） | 材料（只读） | `slices.yaml` + `figures.yaml` | 全量确定 |
| ② 抽取 | **抽取员** | 一个切片 + 矩阵规范 | 该片知识点候选（带出处坐标） | 按片扇出 |
| ② 抽取 | **视觉员** | 一张图 + 前后引用句 | 结构描述 / 重绘 SVG·mermaid / `kind: figure` | 按「被当作解释主体的图」扇出 |
| ③ 归并 | **归并员** | 全部候选 + 现有考纲 | `coverage.yaml` + 考纲 diff | **串行，唯一全局视图** |
| ④ 派工 | **派工脚本**（非 agent） | 矩阵 | 任务表（按知识点打包、`input_hash`） | 确定 |
| ⑤⑥ | **出题单元**：出题员 → 校验员 | 3–6 个知识点 + 原文段落 + 契约 + 已出题清单 | 通过校验的题目 | **单元内串联、单元间并联 ×N** |
| ⑦ 统合 | **统合员** | 全部题目 + 矩阵 | 覆盖率对账、归类、改考纲 | 串行 |
| ⑦ 统合 | **解析脚本**（非 agent） | `questions/*.md` | `relations.yaml` + 入库 | 确定 |

### 编排图

```
材料(只读) → 切片脚本 ──→ 人过目骨架          ← 人介入点 ①
                 │
        ┌────────┴─────────┐
   抽取员 ×N            视觉员 ×M
        └────────┬─────────┘
            归并员（串行·全局）
                 ↓ coverage.yaml + 考纲 diff
            派工脚本 → 任务表
                 ↓
   ┌──────── 出题单元 ×N（并联）────────┐
   │  L1 / L2 / L3 / L4 一视同仁：      │
   │   出题员 → 校验员（独立会话）       │
   │        ↑_____ fail 打回重出 ______ │
   └───────────────┬───────────────────┘
            统合（覆盖率对账 → 归类/改考纲 → 解析关系边 → 入库）
                 → 人裁决                     ← 人介入点 ②
```

### 四条硬约束

1. **「串联」指流程，不指上下文。** 单元内的出题员与校验员**仍是两个独立会话**：校验员的输入是
   文件（题目 + 原文 + 判定表），**不是作者的对话历史**，也**不看 `## 解析`**——否则它就承接了作者的偏见，
   测不出事实错误。这是整条流水线唯一能兜住「自信的误指挥」的地方。
2. **打回重出在单元内闭环**：校验 fail → 同一单元立即重出（`attempts++`）。材料段落已在手，重出很便宜；
   超过上限进 `dead` 队列人工看一眼，不阻塞其它单元。
3. **L1–L4 一视同仁地并行**：L3/L4 也由 agent 出，合并进同一条并联流（不给它们单开串行轨）。
   **只有法式大题例外**——它一题一议，**不进这条流水线**（人来做）。
   但人写的题**进同一份数据**：一样放 `questions/`、一样跑 `check.py`、一样被解析出关系边。
   L4（迁移）题在交付报告里**单独列出请人过目**，那是批量的异步复核，不阻塞流程。
4. **人只出现在两个位置**：骨架过目（切片边界有歧义）+ 归类裁决（考纲兜不住时）。
   其余全自动——预算分析已证明：钱可以忽略，人的时间才是瓶颈（§7）。

### 版本漂移

prompt 与契约要有**版本号**，写进任务记录与题目 front-matter（`author_version` / `contract_version`）。
否则过两个月问「为什么这批题风格不同」，会**无从追查**——契约改过、模型换过、prompt 调过。

## 7. 技术栈与依赖原则

**所有 LLM 能力走 API，不引任何推理框架。** 这条一箭双雕：既省掉本地模型，
也把 `torch` / `transformers` / `sentence-transformers` 那一整片重依赖挡在门外。

### 依赖判据：不看「自己写还是引库」，看重量

三条都过 = 轻，可以用：

1. **安装体积**：GB 级、或需要本地编译工具链 → 不要
2. **是否要拉起外部服务进程**：broker / 数据库 daemon / 图库服务 → 不要
3. **传递依赖数**：会拉进一长串传递依赖 → 不要

因此可以用：`sqlite3`（标准库，含 FTS5 与递归 CTE）· `PyYAML` · `httpx` · `Pillow` ·
`PyMuPDF` · `numpy`。不要用：`torch` / `transformers` / `faiss` / `neo4j` /
`Celery + Redis` / `LangChain` 这一类（体积大、要起服务、或把上下文边界藏进框架内部）。
`python-docx` / `python-pptx` 按需再加。

### 三个接口，provider 只是配置

```
LLMClient     chat(messages, model, json_mode)        # 出题 / 校验 / 归类
VisionClient  image(path, prompt) -> text | svg        # 读图与重绘
Embedder      embed(texts[]) -> vectors（带本地缓存）    # 向量召回
```

三个都走 **OpenAI 兼容**协议，用 `httpx` 直连，**不引各家 SDK**；配置只有三样：
`base_url` / `model` / `api_key`（与后端 `config/ai.local.json` 同构，可直接复用）。
**换 provider 只改配置、不改代码**——"先用某一家"和"将来可换"因此不冲突。

### 三条由此产生的设计约束

- **embedding 必须本地缓存**：索引会频繁重建，走 API 会又慢又花钱。
  按「文本哈希 → 向量」缓存到本地（SQLite 或文件），命中就不调用，重建索引时增量补齐。
- **账本按能力分别记**：chat / vision / embedding 的 token 与费用分开记（视觉按图计费、单价不同），
  限流也按 provider 分别设（并发上限 + 429 退避）。
- **视觉能力只做两件事，都要求它输出代码**：读图（结构化描述 / `kind: figure` 知识点）与
  重绘（**SVG 优先**——浏览器原生渲染、零前端依赖；不要输出位图，也不要输出 mermaid 以外的
  自定义 DSL，除非前端已经能渲染）。

## 8. 执行与成本

**并行/串行分工**：**出题与校验都扇出**（它们按任务包、按题独立）；**派工与统合单发**
（这两步持有全局视图）。四层在这里没有区别——长链条 `problem` 与 `single` 在队列里是同一种任务。
无论用哪个环境，三条硬约束不变：一个任务包一个任务；契约与输出骨架同一份；
**校验必须是独立会话**（另一个 agent、重读原文、**不看作者的解析**，否则会被带偏）。

CodeBuddy 不支持扇出 → 在这个环境里跑就是串行版（同一会话复用契约可以省 token，但慢一个量级）；
需要并行时用支持扇出的工具。

**量级估算**（一本书：30 万 tokens、约 120 道，其中长链条 `problem` 约 6 道）：

| 阶段 | 并行耗时 | 串行耗时 |
|---|---|---|
| 覆盖矩阵 | ~5 min | ~5 min |
| 出题（四层同批） | ~22 min | ~3.8 h |
| 独立校验 | ~14 min | ~2.3 h |
| 统合入库 | ~20 min | ~20 min |
| **合计** | **≈ 1 h wall clock** | **≈ 7 h（实际因会话往返更久）** |

Tokens ≈ 3M（便宜档约 $1、贵档约 $15）。人工 ≈ 1 h：抽检 20 min +
**长链条题的精读**（约 50 页 1 道，一本书通常只有几道）。

**结论：钱可以忽略，人的时间是瓶颈。** 覆盖型题目可以放心出满；
**长链条题要克制**——每一道都实实在在花掉你十几分钟精读。
